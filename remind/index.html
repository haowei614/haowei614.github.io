Requirements reviews take weeks — and conflicts still slip through. 要件レビューには何週間もかかる。それでも矛盾は見逃される。

System and software specifications run to hundreds of pages, written by different teams with different priorities. A safety requirement can quietly contradict a performance target three chapters away. Manual reviews catch what each reviewer knows to look for; cross-cutting conflicts are the ones that survive. システム要件・ソフトウェア要件は数百ページに及び、異なるチームが異なる優先度で書いています。ある安全要件が、別の章の性能目標と静かに矛盾していることもあります。人手のレビューは、各レビュアーが知っている観点では強い一方、観点をまたぐ矛盾ほど残りやすいのが現実です。

Scattered across documentsドキュメントに散在

Related requirements live in different chapters, owners, and versions.関連する要件が、章・担当者・版をまたいで存在する。

Competing priorities相反する優先度

Safety, cost, performance, and schedule pull in different directions.安全性・コスト・性能・スケジュールが互いに引っ張り合う。

Found too late発見が遅い

A conflict found during integration costs far more to fix than one found in review.統合段階で見つかった矛盾は、レビュー段階よりはるかに修正コストが高い。

$100 → $10,000+ same error · review → production 同じ誤り · レビュー → 本番

A requirement error that costs around $100 to fix in review can cost $10,000 or more once it reaches production — the well-known 1:10:100 rule. レビュー段階なら約$100で直せる要件の誤りも、本番に到達すると$10,000以上かかることがあります。これはよく知られた 1:10:100 の法則です。

Decades of studies find that fixing a defect after release runs 10–100× the cost of fixing it during requirements, and requirement errors drive an estimated 70–85% of all project rework. 数十年にわたる研究では、リリース後の修正コストは要件段階の10〜100倍とされ、要件の誤りはプロジェクトの手戻りコストの推定70〜85%を占めます。

Sources: Boehm, Software Engineering Economics (1981); NIST (2002); IBM Rational (2003) 出典: Boehm, Software Engineering Economics (1981); NIST (2002); IBM Rational (2003)

An AI review board, not a single prompt 一つのプロンプトではなく、AIのレビューボード

  1. 1

    Upload your requirements要件をアップロード

    A full specification or selected sections.仕様書全体、または一部の章から。

  2. 2

    Specialized reviewers analyze them専門エージェントが分析

    Each agent owns one concern: safety, consistency, feasibility, quality.安全性・一貫性・実現性・品質など、観点ごとに担当を分けてレビュー。

  3. 3

    Reviewers challenge each otherエージェント同士が議論

    Disagreements are argued out, so findings don't depend on one model's guess.意見の対立を議論で突き詰めるため、単一モデルの判断に依存しない。

  4. 4

    Get actionable findingsすぐ使える指摘を受け取る

    Each issue lists the affected requirements, the reasoning, and a proposed revision.各指摘に、関係する要件・根拠・修正案を添えて提示。

Sample finding 指摘の例
Finding指摘
Conflict: SYS-112 vs SYS-207 矛盾：SYS-112 と SYS-207
Requirements要件
SYS-112: The system shall enter a safe state within 100 ms of sensor loss. SYS-207: The controller shall complete diagnostics before any mode transition. SYS-112：センサ喪失から100 ms以内に安全状態へ移行すること。 SYS-207：モード遷移の前に診断を完了すること。
Why it matters影響
Diagnostics can take longer than 100 ms, so both cannot be met when a sensor is lost. 診断が100 msを超える場合、センサ喪失時に両方を満たせない。
Raised by指摘者
Safety reviewer; challenged and confirmed by Feasibility reviewer 安全性エージェントが指摘、実現性エージェントが検証
Proposed fix修正案
Exempt safe-state transitions from SYS-207, or bound diagnostic time below 100 ms. 安全状態への遷移をSYS-207の対象外とする、または診断時間を100 ms未満に制限する。
